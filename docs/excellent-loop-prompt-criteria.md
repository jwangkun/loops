# 优秀 Loop 提示词应具备的能力与特征

> 本文基于对 2026 年 "loop engineering"（循环工程）领域公开资料的检索与总结，提炼出一份**优质循环提示词（loop prompt）的质量标准**。它是 `prompts/` 目录下全部 100 个中文 + 100 个英文 Loop 的优化参考，也为未来新增 Loop 提供 checklist。

检索来源（节选）：Loop Engineering 指南（Lushbinary）、Ship PR Until Green 解剖（AI Skill Market）、What Is Loop Engineering（KyenAI）、Stop Hand-Holding Your Coding Agent（arXiv 2667.00038）、Build a Coding Agent Loop That Stops Safely（Verdent）、Designing Agent Loops That Converge（Developers Digest）、Loop Control and Exit Conditions（Vercel Engineering Playbook）、Tool Call Convergence（Tian Pan）等。

---

## 一、核心心智模型

一个 Loop 不是"一条更聪明的提示词"，而是一套**闭环控制系统**：

```
运行检查命令 → 观察结果 → 决定下一步 → 执行 → 回到检查命令 → 直到退出条件成立或达到上限
```

优秀 Loop 的衡量标准只有一个：**退出条件是否客观、可验证**。模型是否"觉得自己做完了"永远不能作为退出依据——这是所有失败模式的根源。

## 二、优秀 Loop 提示词的 14 项能力

### 1. 目标是一个"世界状态"，而不是一个"活动"
- ❌ "修复构建"（活动，永远不知道何时结束）
- ✅ "当前分支最新一次 CI 运行 `conclusion=success`"（状态，任一时刻非真即假）
- 用一句话描述 finish line，让 agent 自己找路径，而不是把每一步都写死。

### 2. 退出条件必须客观、机器可验证
- 由检查命令的退出码 / 输出判断，yes/no 明确；绝不依赖 agent 自评。
- 验收标准应是"可执行测试 > 类型/模式检查 > 规则/策略 > 人工评审"，尽量避免用模型当裁判（level-4 判分最弱，若必须用，应由**另一个模型**而非工作者自评）。

### 3. 确定性的检查命令
- 每次迭代之间运行同一命令；命令应幂等、确定性。
- 非确定性 / flaky 检查会让 agent 无限循环：识别已知 flaky 项、行动前先重跑确认、必要时将其排除出验收契约。

### 4. 最大迭代次数（硬性安全带）
- 每个 Loop 必须有迭代上限。它是"成本上限 + 安全护栏"，不是让循环结束的引擎——健康运行里退出条件会先触发。
- 无上限的 Loop 是一个注定会爆账单的 bug。

### 5. 多轴预算（迭代 + token/成本 + 墙钟时间）
- 三者必须同时设置，因为它们以不同方式失败：可能 4 次大上下文耗尽预算，也可能 200 次廉价迭代跑 6 小时。
- 预算耗尽是**计划内的退出路径**（干净收尾、写交接说明），而不是崩溃。

### 6. 收敛 / 防抖动（anti-thrash）检测
- 若同一检查以**相同根因连续两次**失败，说明当前策略无解：应**更换思路或停止上报**，而不是原样重试。
- 这是区分"在收敛"与"在打转"的关键信号。

### 7. 命名化的终态
- 循环只能以 `成功 / 受阻 / 耗尽 / 空操作` 之一结束。
- **错误、停滞、预算耗尽永远不能被报告为成功**。停止很少是凭空编的数字，而是目标达成、停滞触发或预算触顶。

### 8. 独立的验证（maker-checker 分离）
- 验证应是代码（测试 / 编译 / lint / schema），而不是模型给自己打分。
- 当必须用模型判分时，让它在独立上下文里评判，打破共享上下文导致的确认偏误。

### 9. 防作弊护栏（anti-gaming）
- 明确禁止：删除测试、跳过检查、`--no-verify`、调低严格度、`|| true`、改 CI 配置把必检项降级等来"假绿"。
- 优化一个数值时，metric-gaming 是真实失败模式；验收应是"检查真正通过"，而非"命令以任何手段返回 0"。

### 10. 根因优先，而非症状
- 做最小修复，针对根因；避免掩盖（如用 `aria-hidden` 隐藏告警节点）。
- 一次只改一件事（one change per iteration），让每一步可诊断、失败可归因。

### 11. 结构化的失败反馈
- 把失败喂给下一轮时，附上具体内容：哪条检查失败、哪个文件、什么错误、是新失败还是重复失败。
- "它失败了，再试一次"会诱导同样的失败；"这条测试在该函数以该错误失败"才给 agent 可推理的材料。

### 12. 重试升级阶梯（retry escalation）
- 不要无脑重试同一动作。当同一失败重复时，按阶梯升级：
  1. 带反馈重试（同样的思路 + 验证输出）
  2. 刷新上下文重试（总结已学到的，丢弃被污染的转录，干净重来）
  3. 换策略重试（plan 步必须提出与已记录失败**本质不同**的approach）
  4. 升级给人类（交 issue / 总结 / 停止）
- "知道何时放弃"是特性，不是缺陷。

### 13. 人类检查点与边界
- 合并 / 部署 / 删除 / 破坏性操作 / 外部沟通前必须人工批准。
- 范围纪律：只动本次任务相关文件，不碰无关文件。

### 14. 状态持久化（面向长循环）
- 进度写在磁盘 / git / issue 上，而不是对话上下文里（上下文会在 compact 时丢失）。
- 交接记录要带：任务、历史、建议的下一步动作。

## 三、优化本仓库 Loop 时落地的三条原则

针对检索发现的系统性缺口，本次对 `prompts/` 全部 200 个文件统一强化（仅追加、幂等、不改动领域内容）：

1. **收敛保护**：同一检查以相同根因连续两次失败时，换思路或停止上报，而非原样重试。
2. **预算纪律**：遵守宿主 harness 的 token / 成本 / 时间预算；预算耗尽 = 停止并上报信号，而非重试信号。
3. **终态明确**：循环只能以成功 / 受阻 / 耗尽结束；停滞或预算耗尽绝不被报告为成功。

> 实施统计：英文 100/100 文件、中文 100/100 文件均补齐上述原则（其中收敛保护在英文 92 个、中文 97 个文件本已具备，未重复追加）。

## 四、新增 Loop 的自检清单

- [ ] 目标用可观察的"世界状态"描述，而非活动
- [ ] 退出条件由命令/产物客观判定，agent 自评不算数
- [ ] 检查命令确定、幂等，flaky 项已处理
- [ ] 设有最大迭代次数
- [ ] 设有迭代 / 成本 / 时间多轴预算
- [ ] 含收敛 / 防抖动检测（相同根因连续失败则升级或停止）
- [ ] 终态已命名（成功 / 受阻 / 耗尽），耗尽 ≠ 成功
- [ ] 验证独立（代码优先，模型判分须独立上下文）
- [ ] 含防作弊护栏
- [ ] 根因优先、一次一改
- [ ] 失败反馈结构化
- [ ] 含重试升级阶梯
- [ ] 危险操作前设人类检查点
- [ ] 长循环状态落盘
