# 无障碍审计直至清洁

**分类:** 无障碍
**标识符:** `a11y-audit-until-clean`
**最大迭代次数:** 10

## 目标

消除本次变更涉及的路由/页面上的所有严重（serious/critical）无障碍违规，使 `npm run test:a11y`（如 axe）零失败。修复需针对根因，而非仅掩盖工具告警，确保键盘、读屏与对比度等真实可用性均得到改善。

## 适用场景

在新增或修改 UI 组件、页面布局或表单之后，用来验证变更未引入严重无障碍回归。

## 检查命令

```bash
npm run test:a11y
```

## 退出条件

- `npm run test:a11y` 退出码为 0。
- 报告中无 serious / critical 级别违规。
- 中等（moderate/minor）违规若影响核心交互也建议修复。

## 执行步骤

Step 1: 运行 `npm run test:a11y`，捕获每条违规的规则 ID、节点选择器与帮助信息。
Step 2: 分析根因——区分 DOM 顺序问题、缺失语义标签、焦点管理缺失、对比度不足等不同类别；避免只处理单条告警而忽略同类问题。
Step 3: 做最小修复：优先用原生语义元素与正确的 ARIA 角色修根因，不要靠 `aria-hidden` 或空 `alt` 掩盖；保持视觉与行为不变。
Step 4: 重新运行检查命令；若仍有违规且未达最大迭代次数，回到 Step 2。
Step 5: 达到最大迭代仍未通过时停止，汇报剩余违规清单及其根因分析，不要无限循环。

## 常见陷阱

- 治标不治本：用 `aria-hidden` 隐藏告警节点，而非修复语义或焦点顺序。
- 把对比度问题误当 ARIA 问题修——颜色对比需调整背景/前景色，而非加标签。
- 修复一条规则后引入新违规（如补 `alt` 后焦点顺序被打乱），缺少回归验证。
- 自动化工具只能发现约 30–40% 的无障碍问题；自动化通过不等于人工审计通过，不可过度宣称"完全无障碍"。

## 注意事项

- 修复不得改变现有视觉外观与交互行为（除非外观本身就是违规根因，如对比度）。
- 不要降低工具的严格度或跳过规则来通过检查。
- 仅审计并修复本次变更触及的 UI，避免无关的大面积改动。

- 收敛保护：若同一检查以相同根因连续两次迭代失败，应更换思路或停止上报，而非机械地原样重试。
- 预算纪律：遵守宿主 harness 的 token / 成本 / 时间预算；预算耗尽视为「停止并上报」信号，而非重试信号。
- 终态明确：循环只能以「成功 / 受阻 / 耗尽」三种终态结束；停滞或预算耗尽绝不能被报告为成功。
