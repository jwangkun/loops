# 访问权限审查循环

**分类:** 安全与合规
**标识符:** `access-review-loop`
**最大迭代次数:** 20

## 目标

确保每个用户、角色与服务账号的访问授权都有文档化、当前的正当业务理由。过时、过度授权或孤儿状态的访问应被撤销，或正式记录为已审查的例外。成功即审查脚本干净退出，且每个标记项都已作出明确决定。

## 适用场景

定期访问审查、角色/权限变更后，或审计要求证明所有授权均有正当理由时使用。

## 检查命令

```bash
python scripts/access_review.py
```

## 退出条件

- `python scripts/access_review.py` 退出码 0。
- 每个被标记的用户、角色或授权均已被撤销，或已记录正当理由。

## 执行步骤

Step 1: 运行检查，完整捕获输出，列出每个被标记的用户、角色与授权。
Step 2: 逐项核验正当理由：归属人是谁、当前为何存在、范围是否仍为所需最小；区分人类账号与服务/机器账号。
Step 3: 采取最小且正确的动作——撤销无用访问或记录已审查的例外；绝不只因上轮通过就盖章放行。
Step 4: 重新运行检查；若仍有项且未达最大迭代次数，回到 Step 2。
Step 5: 达到最大迭代仍未成功则停止，报告剩余未审查或无理由的授权，不要无限循环。

## 常见陷阱

- 把长期服务账号当作天然安全——它们随时间积累最多过时、过宽的权限。
- 仅因上轮审批通过就再次批准，而非重新核查当前业务需要。
- 嵌套组成员关系掩盖实际权限：某用户表面干净，却通过组继承了广泛访问。
- 管理员或应急（break-glass）账号在非事件期间仍保持启用。

## 注意事项

- 区分撤销与记录为例外；删除线上生产角色前必须确认影响范围。
- 记录每项决定与变更以备审计——这是一项合规活动，而非单纯清理。
