# 分析健康检查

**分类:** 运营与市场  
**标识符:** `analytics-health-check`  
**最大迭代次数:** 8

## 目标
确保所有关键分析事件被正确追踪并通过 `analytics_check.py` 的全部校验。成功意味着每个定义的事件在正确元素上以正确参数触发一次，无缺失、错绑或重复。

## 适用场景
新功能上线、埋点方案变更、跨域/SPA 改造或发现数据异常后，用本循环校验事件追踪基线，避免脏数据污染报表。

## 检查命令

```bash
python scripts/analytics_check.py
```

## 退出条件
- 检查命令以退出码 0 通过，且无 error。
- 全部关键事件存在、在正确元素上触发、参数齐全且无重复触发。

## 执行步骤
Step 1: 运行 `python scripts/analytics_check.py`，完整捕获输出与退出码，记录每条失败的事件名与失败类型。
Step 2: 按失败类型分析：事件缺失、绑定到错误元素、参数缺失/错值、重复触发（多次监听或冒泡未拦截）、跨域/SPA 路由切换丢事件；定位到具体埋点代码与触发位置。
Step 3: 做最小修复：校正单个事件的绑定或参数；优先确保事件在正确元素上触发一次，不得为消除告警而整体禁用事件或静默吞掉异常。
Step 4: 重新运行检查命令；若仍有失败且未达最大迭代次数，回到 Step 2。
Step 5: 若已达最大迭代次数仍未通过，停止并报告剩余失败项（事件、类型、原因、建议），不要无限循环。

## 常见陷阱
- 事件绑定到错误元素（如按钮内层 span 而非按钮本身），导致部分点击漏报。
- 重复触发：同一事件被多次监听或事件冒泡未被拦截，产生重复计数。
- 参数缺失或硬编码错值（如固定 page_name），使分群与漏斗失真。
- SPA 路由切换或弹层打开时未重发 pageview/虚拟页面，漏掉关键浏览。
- 跨域跳转未保留/续传客户端 ID，导致用户旅程断裂。

## 注意事项
- 修复须让真实用户行为被正确捕获，不得为通过检查而禁用或合并语义不同的事件。
- 区分真实缺失与有意下线的事件；下线须有显式记录，不得静默忽略。
- 改动埋点后须在真实环境复现一次触发，确认网络请求与参数符合预期。

- 收敛保护：若同一检查以相同根因连续两次迭代失败，应更换思路或停止上报，而非机械地原样重试。
- 预算纪律：遵守宿主 harness 的 token / 成本 / 时间预算；预算耗尽视为「停止并上报」信号，而非重试信号。
- 终态明确：循环只能以「成功 / 受阻 / 耗尽」三种终态结束；停滞或预算耗尽绝不能被报告为成功。
