# API契约匹配循环

**分类:** API/规范
**标识符:** `api-contract-until-match`
**最大迭代次数:** 10

## 目标

让 API 的实际实现（请求/响应 schema、状态码、字段类型）与已发布的消费者契约完全一致。所有契约测试通过，消费者在升级时不会遇到意外破坏。

## 适用场景

当存在由 Pact 等工具生成的消费者驱动契约测试，且实现端发生改动后需要确认未违反契约时使用。也适用于发布新 API 版本前的回归校验。

## 检查命令

```bash
npm run test:contract
```

## 退出条件

- `npm run test:contract` 退出码为 0。
- 无任何契约验证错误（schema 不匹配、缺失字段、状态码不符等）。
- 所有消费者契约均通过验证。

## 执行步骤

Step 1: 运行 `npm run test:contract`，完整捕获输出，记录失败的契约、对应的消费者、缺失或类型不符的字段。
Step 2: 逐个分析失败项，定位是契约过时还是实现漂移；默认假定实现有错，只有当契约本身确实错误时才修改契约，并同步通知受影响消费者。
Step 3: 用最小 diff 修复：补齐缺失字段、修正类型与状态码、调整必填项；不要伪造数据掩盖失败。
Step 4: 重新运行检查命令；若仍失败且未达最大迭代次数，回到 Step 2。
Step 5: 达到最大迭代次数仍未通过时停止，汇报剩余的失败契约与阻塞原因，不要无限循环。

## 常见陷阱

- 为让测试变绿而修改契约去迁就有缺陷的实现——应优先修复实现。
- 仅修复第一个失败而忽略其余，导致同一根因反复出现。
- 忽略契约中字段的可空性/必填性差异。
- 修改契约后未通知下游消费者，导致隐性破坏。

## 注意事项

- 永远不要删除或绕过失败的契约测试。
- 区分消费者驱动契约与提供者自测，两者语义不同。
- 修改契约属于破坏性变更，需走版本化与通知流程。
- 若失败源于契约本身过时，应明确记录原因再更新。
