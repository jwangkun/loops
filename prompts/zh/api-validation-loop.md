# API输入校验循环

**分类:** 后端与API开发
**标识符:** `api-validation-loop`
**最大迭代次数:** 8

## 目标

确保每个 API 端点在处理业务逻辑前，对请求体、查询参数、路径参数与请求头都执行严格的 schema 校验与输入清理。非法输入被尽早拒绝，不进入下游。

## 适用场景

当新增了端点却缺少校验，或安全扫描/代码审查发现未校验的输入入口时使用。也适用于上线前的输入安全加固。

## 检查命令

```bash
npm run test:api-validation
```

## 退出条件

- `npm run test:api-validation` 退出码为 0。
- 所有公共端点都挂载了 schema 校验中间件。
- 非法输入（类型错误、超长、注入字符等）测试用例均返回 4xx。

## 执行步骤

Step 1: 运行 `npm run test:api-validation`，记录失败用例、未校验的端点路径以及缺失的校验类型。
Step 2: 对照路由清单，确认哪些端点缺少校验中间件、哪些已校验但未覆盖字段或未做清理。
Step 3: 用最小改动为每个缺失端点添加 schema 校验（如 zod/joi/express-validator），并补充输入清理（去空格、转义、长度截断）；不要仅在业务逻辑里做临时判断。
Step 4: 重新运行检查命令；若仍失败且未达最大迭代次数，回到 Step 2。
Step 5: 达到最大迭代次数仍未通过时停止，汇报剩余未校验端点与失败用例，不要无限循环。

## 常见陷阱

- 只校验请求体却忽略查询参数、路径参数或请求头。
- 校验存在但未做清理，导致下游仍受注入字符影响。
- 用宽松类型（如 any 或无约束 string）使 schema 形同虚设。
- 在测试中只覆盖合法输入，缺少非法输入的拒绝路径。

## 注意事项

- 校验必须发生在业务逻辑之前，越早拒绝越好。
- 区分校验（结构正确）与清理（内容安全），两者都需要。
- 不要用 try/catch 吞掉校验错误来"通过"测试。
- 敏感字段（如 ID、金额）需额外做范围与格式约束。
