# 自动TDD循环

**分类:** 开发流程
**标识符:** `autoloop-tdd`
**最大迭代次数:** 20

## 目标

通过严格的测试先行（red-green-refactor）循环，增量实现目标行为，直到所有相关测试通过且无回归。每轮迭代只针对一个尚未实现的行为，保持代码始终可工作。

## 适用场景

从行为描述或验收标准出发实现新功能；为已有代码补齐行为时，逐个行为用失败测试驱动，而非事后补测试。

## 检查命令

```bash
npm test
```

## 退出条件

- 目标行为对应的测试全部通过。
- 没有新增失败或回归的测试。
- 检查命令退出码为 0。

## 执行步骤

Step 1: 运行检查命令，捕获完整输出，确认当前哪些行为尚未通过、哪些测试缺失。
Step 2: 挑选下一个最小的未实现行为，先写一个会失败的测试；明确失败原因必须是"行为未实现"，而非语法错误或断言写错。
Step 3: 编写刚好让该测试通过的最小实现代码，不预判未来需求、不增加未被测试驱动的设计。
Step 4: 重新运行检查命令；若仍有未通过行为且未达到最大迭代次数，回到 Step 2；若全部通过则进入重构。
Step 5: 若达到最大迭代次数仍未实现目标行为，停止并报告剩余的失败测试与阻塞原因，不要无限循环或用桩代码掩盖失败。

## 常见陷阱

- 先写实现再补测试：这不是 TDD，测试只会复述实现而非描述行为。
- 在红灯阶段做大规模重构：在测试不通过时改动多处，失败原因会被污染。
- 一个测试覆盖多个行为：失败时无法定位，应拆成最小行为单元。

## 注意事项

- 重构只能在全部测试绿灯时进行，且不改变对外行为。
- 不要为了让测试通过而删除或弱化断言。
- 每次提交保持红灯→绿灯→重构的清晰边界。

- 收敛保护：若同一检查以相同根因连续两次迭代失败，应更换思路或停止上报，而非机械地原样重试。
- 预算纪律：遵守宿主 harness 的 token / 成本 / 时间预算；预算耗尽视为「停止并上报」信号，而非重试信号。
- 终态明确：循环只能以「成功 / 受阻 / 耗尽」三种终态结束；停滞或预算耗尽绝不能被报告为成功。
