# 备份验证循环

**分类:** 数据库与数据
**标识符:** `backup-verify-loop`
**最大迭代次数:** 3

## 目标

证明最新数据库备份可成功恢复到临时实例，并执行基本冒烟查询通过——备份文件存在不等于可恢复，唯一可靠的证据是一次成功的恢复与查询。成功意味着该备份在灾难发生时可被真正使用。

## 适用场景

备份任务运行后、定期灾备演练、或修改备份/恢复流程后，用于确认备份实际可用。

## 检查命令

```bash
npm run db:backup:verify
```

## 退出条件

- 备份文件存在、完整且可被解析。
- 恢复到隔离的临时实例成功，无错误。
- 冒烟查询（关键表行数、最近时间戳、约束有效性）返回符合预期的结果。

## 执行步骤

Step 1: 运行 `npm run db:backup:verify`，捕获恢复过程与冒烟查询的完整输出。
Step 2: 若失败，分类原因——常见为备份文件截断/损坏、格式与恢复工具版本不匹配、临时实例未干净初始化、或冒烟查询因 schema 漂移而报错。逐一修复根因。
Step 3: 应用最小修复（如重生成备份、修正恢复参数、对齐 schema）后重跑；不要靠放宽冒烟查询阈值或跳过校验来制造假绿。
Step 4: 若仍失败且未达最大迭代次数（3），回到 Step 2。
Step 5: 达到最大迭代次数仍未通过时，停止并明确报告该备份不可用——这是必须人工介入的严重问题；禁止无限循环。

## 常见陷阱

- 仅验证文件存在：文件大小正常不代表内容可恢复，恢复才是唯一证据。
- 恢复到生产实例：临时实例必须完全隔离，避免污染真实数据。
- Schema 漂移：备份与当前代码 schema 不一致，导致查询失败却未被察觉。
- 冒烟查询过弱：只查 `SELECT 1`，无法发现真实数据损坏。

## 注意事项

- 恢复必须使用与生产隔离的临时实例，绝不写入生产数据库。
- 验证完成后清理临时实例，避免残留与资源浪费。
- 备份不可用属于高优先级问题，应立即上报而非静默重试。

- 收敛保护：若同一检查以相同根因连续两次迭代失败，应更换思路或停止上报，而非机械地原样重试。
- 预算纪律：遵守宿主 harness 的 token / 成本 / 时间预算；预算耗尽视为「停止并上报」信号，而非重试信号。
- 终态明确：循环只能以「成功 / 受阻 / 耗尽」三种终态结束；停滞或预算耗尽绝不能被报告为成功。
