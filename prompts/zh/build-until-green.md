# 构建直到成功

**分类:** 持续集成/持续部署
**标识符:** `build-until-green`
**最大迭代次数:** 5

## 目标

让生产构建命令以退出码 0 成功完成，产出可用的构建产物（如 `dist/`、`build/`）。成功意味着类型检查、编译、打包、tree-shaking 全链路无错误，而不仅是跳过错误。

## 适用场景

本地或 CI 中验证可发布性时使用；适合在依赖升级、配置改动、大量代码改动后，迭代修复直到构建产出干净可用。

## 检查命令

```bash
npm run build
```

## 退出条件

- `npm run build` 退出码为 0。
- 构建产物已生成且非空（如 `dist/` 或 `build/` 目录存在且包含预期文件）。
- 输出中无错误、无未解析的 import、无类型错误。

## 执行步骤

Step 1: 运行检查命令，捕获完整 stdout/stderr 与退出码，并确认构建产物目录。
Step 2: 分析首个错误：定位是类型错误、导入路径错误、依赖缺失、构建配置（webpack/vite/tsconfig）问题，还是环境变量/平台（Node 版本）问题。优先修第一个错误，因为后续错误常是连锁反应。
Step 3: 做最小修复——修正类型/导入、补装或锁定依赖版本、调整构建配置。绝不要通过 `// @ts-ignore`、关闭类型检查、空实现或 try/catch 吞错来让构建通过。
Step 4: 重新运行检查命令；若仍失败且未超过最大迭代次数，回到 Step 2。
Step 5: 达到最大迭代仍未通过时停止，列出剩余错误及对应文件，并标注疑似根因类型（类型/依赖/配置/环境）。不要无限循环。

## 常见陷阱

- 用 `// @ts-ignore`、`as any` 或关闭类型检查掩盖类型错误，构建变绿但运行时崩。
- 依赖版本漂移（lockfile 不一致）导致本地绿、CI 红，或反之。
- 忽略构建警告（如循环依赖、未使用导出），它们往往是下一个错误的预兆。
- 修了表面错误却未看清是连锁反应的源头，反复在同一文件打转。

## 注意事项

- 构建产物用于生产，修复时不要引入仅开发环境可用的逻辑。
- 不要为通过构建而临时降级依赖或关闭安全/优化选项。
- 若错误源于 Node 版本等环境差异，应同步对齐环境而非绕过。

- 收敛保护：若同一检查以相同根因连续两次迭代失败，应更换思路或停止上报，而非机械地原样重试。
- 预算纪律：遵守宿主 harness 的 token / 成本 / 时间预算；预算耗尽视为「停止并上报」信号，而非重试信号。
- 终态明确：循环只能以「成功 / 受阻 / 耗尽」三种终态结束；停滞或预算耗尽绝不能被报告为成功。
