# 代码审查直到干净

**分类:** 代码质量
**标识符:** `code-review-until-clean`
**最大迭代次数:** 5

## 目标

让目标代码通过 `review_checklist.py` 的全部审查项，产出可合并、无遗留告警的代码。每一轮判定都必须基于真实的命令输出，而非主观印象。

## 适用场景

在提交 PR 或合并到主干前，对新增/改动代码进行结构化质量把关时使用。

## 检查命令

```bash
python scripts/review_checklist.py
```

## 退出条件

- 审查命令退出码为 0。
- 输出中不再出现任何 WARNING / ERROR / FAIL 标记。
- 达到最大迭代次数仍未干净时，停止并汇报剩余阻塞项。

## 执行步骤

Step 1: 运行 `python scripts/review_checklist.py`，完整捕获 stdout/stderr 与退出码。
Step 2: 逐条解析被标记的问题，按文件、规则、行号归类，区分"必须修复"与"风格建议"。
Step 3: 对每个必须修复项应用最小改动；只修问题本身，不顺带重写无关代码。
Step 4: 重新运行检查命令；若仍有失败且未达 5 次，回到 Step 2。
Step 5: 达到 5 次仍未干净时停止，列出剩余未通过项及原因，绝不继续空转。

## 常见陷阱

- 用注释或 `// eslint-disable` 之类的方式压制告警，而非修复根因。
- 把多条问题塞进一次大改，导致审查结果难以归因、回滚困难。
- 只修首个失败项就重跑，忽略其余同类问题，迭代次数被白白消耗。

## 注意事项

- 每轮只针对当前输出的真实问题，不臆造或预防式重构。
- 保持改动聚焦于审查清单覆盖的范围，不扩大 scope。
- 修复优先于豁免；确需豁免时必须附带理由说明。

- 收敛保护：若同一检查以相同根因连续两次迭代失败，应更换思路或停止上报，而非机械地原样重试。
- 预算纪律：遵守宿主 harness 的 token / 成本 / 时间预算；预算耗尽视为「停止并上报」信号，而非重试信号。
- 终态明确：循环只能以「成功 / 受阻 / 耗尽」三种终态结束；停滞或预算耗尽绝不能被报告为成功。
