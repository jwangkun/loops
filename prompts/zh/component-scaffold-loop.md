# 组件脚手架循环

**分类:** 代码生成与重构
**标识符:** `component-scaffold-loop`
**最大迭代次数:** 5

## 目标

为指定组件名生成完整、可运行的脚手架：组件实现文件、对应的测试、以及展示用的 stories，并使检查命令通过。产出应遵循项目既有组件的目录结构与命名约定。

## 适用场景

需要新建一个 UI 组件并立刻具备测试与可视化 stories 时；组件名以 `<component-name>` 传入。

## 检查命令

```bash
npm test -- <component-name>
```

## 退出条件

- 组件实现文件、测试文件、stories 文件均已生成。
- 测试通过，检查命令退出码为 0。
- 与项目现有组件结构与命名一致。

## 执行步骤

Step 1: 参考项目中最相近的已有组件，运行检查命令确认脚手架基线，捕获缺失文件与失败。
Step 2: 识别组件应有的 props/状态与渲染变体，据此列出测试用例与 stories 的展示场景。
Step 3: 生成组件实现、测试与 stories，复用项目既有模式（样式方案、导出方式、类型定义）。
Step 4: 重新运行检查命令；若仍有失败或缺失且未达最大迭代次数，回到 Step 2 修正。
Step 5: 若达到最大迭代次数仍有未通过项，停止并报告缺失文件与失败测试，不要遗留半成品或用空实现骗过检查。

## 常见陷阱

- 忽略现有约定：自创目录/命名/样式方案，导致组件无法被项目消费。
- stories 只展示一种状态：遗漏关键 props 变体，可视化回归形同虚设。
- 测试只验证渲染不抛错：未断言实际 DOM/行为，无法捕获真实回归。

## 注意事项

- 优先模仿既有组件而非引入新依赖。
- 组件须类型安全且导出清晰，便于被其它模块导入。
- 不要为通过检查而留 TODO 或空桩实现。

- 收敛保护：若同一检查以相同根因连续两次迭代失败，应更换思路或停止上报，而非机械地原样重试。
- 预算纪律：遵守宿主 harness 的 token / 成本 / 时间预算；预算耗尽视为「停止并上报」信号，而非重试信号。
- 终态明确：循环只能以「成功 / 受阻 / 耗尽」三种终态结束；停滞或预算耗尽绝不能被报告为成功。
