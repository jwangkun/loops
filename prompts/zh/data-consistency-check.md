# 数据一致性检查

**分类:** 数据库与数据
**标识符:** `data-consistency-check`
**最大迭代次数:** 5

## 目标

确保数据集中不存在孤立记录、外键违规或约束失效——每一类一致性断言都通过。成功意味着数据处于自洽状态，可安全用于查询、报表与下游处理。

## 适用场景

数据迁移后、软删除批量操作后、或定期数据健康巡检时，用于发现并修复累积的引用与约束问题。

## 检查命令

```bash
npm run db:consistency
```

## 退出条件

- 所有一致性检查均通过，退出码为 0。
- 报告中违规计数为 0（无孤立记录、无外键失效、无唯一约束冲突）。

## 执行步骤

Step 1: 运行 `npm run db:consistency`，捕获完整报告（含违规表、行数与类别）。
Step 2: 按类别分析违规——软删除产生的孤儿记录、缺失级联规则导致的外键断裂、并发写入引起的唯一冲突等。定位根因而非仅删除报错行。
Step 3: 应用最小数据修复（重新关联孤儿记录、补全级联、去重），或修正缺失的约束/级联规则；不要靠放宽检查或加 `WHERE` 排除来掩盖。
Step 4: 重跑检查；若仍有违规且未达最大迭代次数（5），回到 Step 2。
Step 5: 达到最大迭代次数仍未通过时，停止并列出剩余违规类别与影响范围；禁止无限循环或静默忽略。

## 常见陷阱

- 软删除产生孤儿：父记录软删除但子记录仍引用，常规外键检查发现不了。
- 仅删除报错行：掩盖根因，问题会在新数据上再次出现。
- 检查与生产 schema 不符：检查脚本基于旧 schema，漏检新增表/约束。
- 顺序敏感：并发写入在检查期间产生瞬时违规，需区分真实损坏与事务时序。

## 注意事项

- 修复前先备份受影响数据，数据修复不可逆。
- 区分需要修代码（约束/级联缺失）还是修数据，避免只补数据而留下漏洞。
- 大表检查可能耗时，注意运行窗口与锁影响。

- 收敛保护：若同一检查以相同根因连续两次迭代失败，应更换思路或停止上报，而非机械地原样重试。
- 预算纪律：遵守宿主 harness 的 token / 成本 / 时间预算；预算耗尽视为「停止并上报」信号，而非重试信号。
- 终态明确：循环只能以「成功 / 受阻 / 耗尽」三种终态结束；停滞或预算耗尽绝不能被报告为成功。
