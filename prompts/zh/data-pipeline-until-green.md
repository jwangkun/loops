# 数据管道直到成功

**分类:** 数据科学与分析
**标识符:** `data-pipeline-until-green`
**最大迭代次数:** 10

## 目标

让数据管道端到端完整运行，无异常退出、退出码为 0，且各阶段（抽取、转换、加载/校验）均按预期完成并产出数据。成功意味着管道在当前数据与配置下真正可重复执行。

## 适用场景

管道代码、SQL/转换逻辑、上游数据源或调度配置发生变更后使用；适合在发布或定时调度前迭代修复直到管道可干净跑通。

## 检查命令

```bash
python scripts/run_pipeline.py
```

## 退出条件

- `python scripts/run_pipeline.py` 退出码为 0。
- 各阶段均执行且无未捕获异常。
- 输出数据已生成且行数/校验在合理范围（非空、非异常归零、符合预期量级）。

## 执行步骤

Step 1: 运行检查命令，捕获完整 stdout/stderr、退出码及各阶段日志/耗时；注意失败发生在哪个阶段。
Step 2: 分析失败：区分代码缺陷（SQL 语法/字段错误、转换逻辑、类型不匹配）、数据问题（上游 schema 变更、空值/脏数据、量级突变）、环境问题（依赖缺失、连接失败、凭证/权限、内存/磁盘不足）。优先确认是数据问题还是代码问题，避免误修。
Step 3: 做最小修复——修正 SQL/转换逻辑、补全依赖或连接配置、对脏数据加显式校验。绝不要用空 try/except 吞错、跳过失败阶段或把异常降级为警告来让管道"通过"。
Step 4: 重新运行检查命令；若仍失败且未超过最大迭代次数，回到 Step 2。
Step 5: 达到最大迭代仍未通过时停止，列出剩余失败阶段、错误信息及根因分类（代码/数据/环境），并标注对下游产出的影响。不要无限循环。

## 常见陷阱

- 用空 `except: pass` 吞掉异常，管道"成功"但数据缺失或错误，污染下游。
- 上游 schema 变更（字段改名/删除）导致字段缺失，被误判为代码 bug 反复改代码。
- 静默截断或类型强转（如 `NaN`→`0`、字符串→数字）掩盖真实脏数据。
- 本地小数据集跑通，但全量数据因内存/超时失败；需用代表性数据量验证。
- 重复运行未做幂等处理，部分写已有数据被重复写入，校验行数虚高。

## 注意事项

- 修复前确认失败可复现，避免针对偶发（网络抖动）做代码改动。
- 不要为通过而放宽数据校验阈值或注释掉断言。
- 涉及生产数据写入时，确保改动幂等，避免重复运行造成数据重复或覆盖。

- 收敛保护：若同一检查以相同根因连续两次迭代失败，应更换思路或停止上报，而非机械地原样重试。
- 预算纪律：遵守宿主 harness 的 token / 成本 / 时间预算；预算耗尽视为「停止并上报」信号，而非重试信号。
- 终态明确：循环只能以「成功 / 受阻 / 耗尽」三种终态结束；停滞或预算耗尽绝不能被报告为成功。
