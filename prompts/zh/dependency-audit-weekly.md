# 每周依赖审计

**分类:** 依赖管理
**标识符:** `dependency-audit-weekly`
**最大迭代次数:** 1

## 目标

生成一份结构化的每周依赖审计摘要：列出过时依赖、按风险与类别分组、并给出分阶段的升级建议（含安全优先项）。成功意味着团队据此清楚本周该升级什么、风险何在。

## 适用场景

每周例行依赖健康巡检，或在发布前评估依赖风险与技术债时使用。

## 检查命令

```bash
npm outdated || true
```

## 退出条件

- 审计摘要已交付，覆盖所有过时依赖。
- 每项含当前版本、最新版本、落后主版本数、风险评级与建议动作。

## 执行步骤

Step 1: 运行 `npm outdated || true`（`|| true` 确保有过期项时也不中断），完整捕获输出表。
Step 2: 结合 `npm audit`（若可用）标注安全漏洞；按类别分析：安全/合规、大版本落后（高风险破坏）、小版本/补丁（低风险）。识别 peer 与传递依赖中的隐患。
Step 3: 撰写最小而完整的报告——分阶段升级计划（先安全、再破坏性、最后低风险），每项标注优先级与潜在影响；不要为凑数而夸大或臆造风险。
Step 4: 重新核对版本与漏洞数据确保准确；本循环为单次（最大 1 次），不重复执行修复。
Step 5: 若关键数据缺失（如 audit 不可用），停止并报告缺失项与降级方案；禁止凭空补全。

## 常见陷阱

- 把"过时"等同于"有风险"：补丁版本落后通常低风险，需区分。
- 忽略安全维度：仅看 `npm outdated` 而漏掉 `npm audit` 的漏洞信息。
- 报告堆砌版本号无优先级：团队无法判断从何下手。
- 忽视 peer/传递依赖：直接依赖正常但传递依赖藏有已知漏洞。

## 注意事项

- 本循环只产出报告与建议，不执行实际升级（升级请用 `dependency-upgrade-one-by-one`）。
- 数据以命令实际输出为准，不要凭记忆或缓存填写版本号。
- 明确标注审计时间窗口与数据来源，便于追溯。
