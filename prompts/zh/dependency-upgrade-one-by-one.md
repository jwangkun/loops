# 依赖逐个升级

**分类:** 依赖管理
**标识符:** `dependency-upgrade-one-by-one`
**最大迭代次数:** 10

## 目标

将关键过时依赖逐个升级到最新可用版本，每个升级后 `npm test` 与 `npm run build` 均通过。成功意味着依赖现代化且主干保持绿色，每一步都可独立回退，便于二分定位问题。

## 适用场景

依赖老化积累技术债、出现安全公告、或准备框架大版本升级前，用于稳步推进现代化。

## 检查命令

```bash
npm outdated && npm test && npm run build
```

## 退出条件

- `npm test` 与 `npm run build` 均退出码 0。
- 选定范围内的过时依赖均已升级（或明确记录为暂不升级及原因）。

## 执行步骤

Step 1: 运行检查命令，捕获 `npm outdated` 输出与测试/构建结果。
Step 2: 从列表中选取单个包优先升级（优先安全公告、其次大版本落后、最后小版本），分析其 CHANGELOG/迁移指南以预判破坏性变更。一次只动一个包——同时升级多个会破坏二分定位能力。
Step 3: 升级该单一包，针对破坏性 API 做最小适配代码修改；不要为通过测试而降级、pin 旧版或跳过测试。
Step 4: 重跑 `npm test && npm run build`；若失败且未达最大迭代次数（10），回到 Step 2 继续修复当前包。每个包绿色后单独提交，便于回退。
Step 5: 达到最大迭代次数仍有未通过的包时，停止并报告已升级包、卡住的包及阻塞原因；禁止无限循环。

## 常见陷阱

- 一次升级多个包：一旦测试失败无法定位是哪个包导致，破坏二分能力。
- 跳过 CHANGELOG：错过破坏性变更与必需的迁移步骤。
- 为通过测试 pin 旧版或删除测试：制造假绿，掩盖真实不兼容。
- 忽略 peer/传递依赖：直接依赖升级后 peer 不匹配，运行时才暴露。

## 注意事项

- 每个包一次提交，commit message 标明包名与版本，便于回退与审计。
- 锁文件（lockfile）需一并提交，避免他人安装到不一致的版本。
- 涉及安全公告的包优先，但同样遵循一次一个的原则。

- 收敛保护：若同一检查以相同根因连续两次迭代失败，应更换思路或停止上报，而非机械地原样重试。
- 预算纪律：遵守宿主 harness 的 token / 成本 / 时间预算；预算耗尽视为「停止并上报」信号，而非重试信号。
- 终态明确：循环只能以「成功 / 受阻 / 耗尽」三种终态结束；停滞或预算耗尽绝不能被报告为成功。
