# 部署验证循环

**分类:** 部署
**标识符:** `deploy-verification-loop`
**最大迭代次数:** 5

## 目标

确认部署后所有健康与冒烟端点返回成功，证明新版本已上线并正确服务。单次绿色检查不足够——要验证实际服务的版本，而非缓存或陈旧实例。成功即检查命令对所有已配置端点退出码为 0。

## 适用场景

部署、回滚或配置变更之后、宣布发布完成之前立即使用。

## 检查命令

```bash
curl -fsS <your-health-url>
```

## 退出条件

- `curl -fsS <your-health-url>` 退出码 0。
- 健康与冒烟端点对新版本返回预期的成功状态与响应体。

## 执行步骤

Step 1: 运行检查，捕获 HTTP 状态、响应体及任何服务版本头；对每个健康/冒烟 URL 逐一执行。
Step 2: 若检查失败，读取部署与应用日志定位原因（发布失败、配置错误、依赖缺失、崩溃循环）；确认访问的是新版本，而非缓存/旧实例。
Step 3: 采取最小修复（修正配置、重启 pod、修复已部署产物）；绝不通过放宽超时或改指向其他 URL 来掩盖失败。
Step 4: 重新运行检查；若仍失败且未达最大迭代次数，回到 Step 2。
Step 5: 达到最大迭代仍未成功则停止，建议回滚而非继续修复，不要无限循环。

## 常见陷阱

- 健康端点返回 200，但应用在 CDN/缓存背后已损坏，或旧 pod 仍在服务流量。
- 在新副本集真正承接流量前就去检查负载均衡器健康状态。
- 定时炸弹式失败：部署后立即健康，但几分钟后退化（连接池、缓存预热）——单次过早检查会误导。
- 冒烟测试只覆盖正常路径，漏掉下游依赖已退化。

## 注意事项

- 确认实际服务的构建/版本，而不仅仅是 2xx 状态，避免验证陈旧实例。
- 当失败风险高或原因不明时，优先回滚而非继续修复迭代。
