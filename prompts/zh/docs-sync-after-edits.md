# 文档同步

**分类:** 文档
**标识符:** `docs-sync-after-edits`
**最大迭代次数:** 5

## 目标

让文档与当前分支相对 `main` 的代码变更保持一致：新增的公开 API、行为或配置项在文档中可查，被移除或重命名的项在文档中同步删除或更新，不留过时内容。

## 适用场景

完成一轮代码编辑后，需要在合并前确保 README、API 文档与代码实际行为相符。

## 检查命令

```bash
git diff main...HEAD --name-only
```

## 退出条件

- diff 中每个代码改动对应的文档都已检查并按需更新。
- 文档不再描述已删除/重命名的 API、参数或配置项。

## 执行步骤

Step 1: 运行检查命令，列出本分支相对 `main` 改动的全部文件，区分代码文件与文档文件。
Step 2: 逐个代码改动判断是否影响公开行为（API 签名、参数、配置、CLI 用法、README 示例），找出受影响的文档位置。
Step 3: 做最小且准确的文档更新：新增项补充说明，移除/重命名项同步删除或改写，绝不保留已失效的示例。
Step 4: 重新运行检查命令并复核文档，确认每处代码改动都已覆盖；未完成且未达最大迭代则回到 Step 2。
Step 5: 达到最大迭代仍有不一致时停止，报告未覆盖的代码改动与对应文档位置，不得无限循环。

## 常见陷阱

- 文档里描述的 API 已在代码中被删除或重命名，却未同步更新，误导使用者。
- 只改了新增内容，遗漏对默认值、错误码、参数顺序等细节的同步。
- 复制粘贴代码示例后不验证其与当前代码是否一致，导致示例失效。
- 把内部实现细节写进面向用户的文档，造成噪音。

## 注意事项

- 文档示例需与代码中的真实签名/输出一致，能直接复制使用。
- 优先更新面向用户的文档；内部架构说明按需处理。

- 收敛保护：若同一检查以相同根因连续两次迭代失败，应更换思路或停止上报，而非机械地原样重试。
- 预算纪律：遵守宿主 harness 的 token / 成本 / 时间预算；预算耗尽视为「停止并上报」信号，而非重试信号。
- 终态明确：循环只能以「成功 / 受阻 / 耗尽」三种终态结束；停滞或预算耗尽绝不能被报告为成功。
