# E2E 测试直到通过

**分类:** 测试
**标识符:** `e2e-until-green`
**最大迭代次数:** 10

## 目标

让端到端测试套件在干净的环境下完整运行并通过，退出码为 0。成功指修复了真实缺陷或脆弱的用例，而非用 sleep、降低断言强度或跳过用例来掩盖。

## 适用场景

CI 中 E2E 套件出现失败，需要逐个修复 spec 并稳定整条流水线时。适合用例数可控、可按 spec 隔离运行的场景。

## 检查命令

```bash
npm run test:e2e
```

## 退出条件

- `npm run test:e2e` 退出码为 0。
- 所有 spec 全部通过，无跳过、无超时、无重试才通过的用例。
- 未达到最大迭代次数上限。

## 执行步骤

Step 1: 运行 `npm run test:e2e`，按 spec 收集失败列表、截图、trace 与控制台错误。
Step 2: 取第一个失败 spec，分析根因：是选择器失效、时序竞态、真实业务缺陷，还是测试固有的脆弱性。
Step 3: 做最小修复：更新失效选择器、加入可靠的等待条件（而非固定 sleep）、修真实缺陷或修正测试本身；严禁为通过而跳过用例或放宽断言。
Step 4: 重新运行 `npm run test:e2e`；若仍有失败且未达上限，回到 Step 2。
Step 5: 若达到最大迭代次数仍未通过，停止并报告剩余失败 spec、已尝试修复与推测根因；绝不无限循环。

## 常见陷阱

- 用固定 sleep 代替确定性等待：延迟掩盖问题且会让套件变慢、不稳定。
- 选择器脆弱：依赖动态生成的 class 或 nth-child，一点 UI 调整即失效。
- 把环境/数据问题当用例缺陷：数据库残留、外部 API 抖动会制造假失败。

## 注意事项

- 不要通过跳过、注释或降低断言严格度来达成绿灯。
- 区分真实失败与 flaky：可疑时单独重跑该 spec 验证。
- 每轮聚焦一个 spec 的最小改动，避免回归。

- 收敛保护：若同一检查以相同根因连续两次迭代失败，应更换思路或停止上报，而非机械地原样重试。
- 预算纪律：遵守宿主 harness 的 token / 成本 / 时间预算；预算耗尽视为「停止并上报」信号，而非重试信号。
- 终态明确：循环只能以「成功 / 受阻 / 耗尽」三种终态结束；停滞或预算耗尽绝不能被报告为成功。
