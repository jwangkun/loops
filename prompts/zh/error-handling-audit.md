# 错误处理审计

**分类:** 代码质量
**标识符:** `error-handling-audit`
**最大迭代次数:** 8

## 目标

让所有公共函数具备一致、明确的错误处理：无吞掉的异常、无未处理的 Promise 拒绝、错误以统一方式记录与传播。最终由 lint 与测试共同验证。

## 适用场景

当模块的错误处理风格混乱（混用 try/catch、裸 catch、`async/await` 未处理拒绝、错误被静默吞掉）时使用，作为发布前的稳健性关卡。

## 检查命令

```bash
npm run lint && npm test
```

## 退出条件

- `npm run lint` 与 `npm test` 均退出码为 0。
- 不再存在以下模式：空 catch、吞掉错误、`async` 函数无拒绝处理、返回 `undefined` 代替错误。
- 新增/修正的错误路径均有对应测试覆盖。
- 达到 8 次仍有遗留时停止并汇报。

## 执行步骤

Step 1: 运行 `npm run lint && npm test`，捕获失败项与告警。
Step 2: 扫描被标记函数及同类可疑函数，逐个判定：该错误应向上传播、应记录后传播，还是应就地恢复？给出明确策略。
Step 3: 对每个函数应用最小改动以落实策略（添加 catch、转换错误类型、补充日志、修正测试）；绝不通过 `catch {}` 或 `Promise.catch(()=>{})` 把错误抹掉。
Step 4: 重新运行检查命令；若仍有失败且未达 8 次，回到 Step 2。
Step 5: 达到 8 次仍有遗留，停止并列出剩余未处理路径与建议策略。

## 常见陷阱

- 把异常吞成静默成功，导致上游无法感知失败。
- catch 后只打日志却未重新抛出，调用方误以为成功。
- 对所有错误一律转成通用 Error，丢失原始错误类型与堆栈。
- 只补 happy-path 测试，错误路径仍未被验证。

## 注意事项

- 错误处理策略须在模块内一致：传播、记录、恢复三选一并显式声明。
- 保留原始错误链（cause/wrapped error），便于排查。
- 不得为通过 lint 而把规则豁免加在函数顶部。
- 改动错误行为属语义变更，必须同步更新调用方与测试。

- 收敛保护：若同一检查以相同根因连续两次迭代失败，应更换思路或停止上报，而非机械地原样重试。
- 预算纪律：遵守宿主 harness 的 token / 成本 / 时间预算；预算耗尽视为「停止并上报」信号，而非重试信号。
- 终态明确：循环只能以「成功 / 受阻 / 耗尽」三种终态结束；停滞或预算耗尽绝不能被报告为成功。
