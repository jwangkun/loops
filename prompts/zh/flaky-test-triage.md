# Flaky 测试分类

**分类:** 测试
**标识符:** `flaky-test-triage`
**最大迭代次数:** 8

## 目标

对指定失败套件中的每个失败用例，给出明确的分类结论：flaky（非确定性）还是 real（真实缺陷）。真实缺陷必须修复到稳定通过；flaky 用例须指出不确定来源并稳定化，而非简单跳过。

## 适用场景

某测试套件失败，但无法判断是真 bug 还是偶发（时序、顺序、共享状态、外部依赖）时，用于在动手修复前先分类、再定向处理。

## 检查命令

```bash
npm test -- --testPathPattern=<failing-suite>
```

## 退出条件

- 套件中每个失败用例都已分类为 flaky 或 real。
- 标记为 real 的用例已修复并通过；标记为 flaky 的用例已稳定化或记录明确的不确定来源。
- 未达到最大迭代次数上限。

## 执行步骤

Step 1: 多次运行 `npm test -- --testPathPattern=<failing-suite>`（建议至少 5 次），记录每次的通过与失败组合。
Step 2: 分析失败模式：恒定失败 → real；间歇失败 → flaky。对 flaky 排查时序、共享状态、执行顺序、随机数据、外部 API/时间/时区依赖。
Step 3: 对 real 用例做最小根因修复；对 flaky 用例消除不确定来源（确定性等待、隔离状态、固定随机种子），而非跳过或加 sleep。
Step 4: 重新多次运行该套件验证稳定性；若仍有未分类或未稳定的失败且未达上限，回到 Step 2。
Step 5: 若达到最大迭代次数仍有未分类/未稳定项，停止并报告每个剩余用例的证据（失败模式、复现条件）与推测根因；绝不无限循环。

## 常见陷阱

- 一次失败就判定 flaky：单次失败更可能是真实缺陷，需多次运行才能区分。
- 仅在隔离运行下验证：flaky 常由顺序/共享状态触发，必须全量套件多次运行。
- 把外部 API 抖动当成测试稳定：掩盖了真实的不确定性来源。

## 注意事项

- 不要通过重试阈值或跳过用例来"解决"flaky。
- 分类必须基于证据（失败模式、复现条件），不可凭感觉。
- 稳定化优先于跳过；确实无法稳定时再记录并人工跟进。
