# 格式化直到干净

**分类:** 代码质量  
**标识符:** `format-until-clean`  
**最大迭代次数:** 3

## 目标
格式化工具运行后代码无任何待改动项，退出码为 0，且 diff 为空。任何无法被工具自动修正的问题已用最小的人工改动解决，使后续重复运行保持幂等无变更。成功即代码已完全符合项目的格式规范。

## 适用场景
提交或合并前，或当格式化工具报告有文件需要改动时使用。

## 检查命令

```bash
npm run format
```

## 退出条件
- `npm run format` 退出码 0
- 重复运行后无文件被改动（幂等，diff 为空）

## 执行步骤
Step 1: 运行格式化工具，捕获输出，列出被改动的文件。
Step 2: 区分工具已自动修复的部分与仍报错/无法解析的部分；对于无法解析的情况定位根因（语法错误、冲突配置、文件类型未纳入）。
Step 3: 对工具无法修复的项做最小人工改动（通常是修语法错误或修正配置），不要与格式化器对抗式手写代码。
Step 4: 重新运行格式化工具；若仍有改动且未达最大迭代次数，回到 Step 2。
Step 5: 达到最大迭代仍未干净则停止，报告剩余无法解析的文件与原因，不要无限循环。

## 常见陷阱
- 与格式化器对抗，手写它随后会撤销的代码，导致无限抖动。
- 格式化工具因语法错误而跳过文件，却误以为格式已通过。
- 多个格式化器（Prettier 与 ESLint 格式规则）配置冲突，互相覆写。

## 注意事项
- 仅提交格式化引起的改动，避免借机夹带逻辑改动。
- 若需修改格式化配置，应在循环之外单独进行并评估全局影响。

- 收敛保护：若同一检查以相同根因连续两次迭代失败，应更换思路或停止上报，而非机械地原样重试。
- 预算纪律：遵守宿主 harness 的 token / 成本 / 时间预算；预算耗尽视为「停止并上报」信号，而非重试信号。
- 终态明确：循环只能以「成功 / 受阻 / 耗尽」三种终态结束；停滞或预算耗尽绝不能被报告为成功。
