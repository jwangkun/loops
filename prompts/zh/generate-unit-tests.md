# 生成单元测试

**分类:** 代码生成与重构
**标识符:** `generate-unit-tests`
**最大迭代次数:** 5

## 目标

为目标函数生成一组稳定的单元测试，覆盖正常路径、边界条件和错误路径，并使其在检查命令中全部通过。测试应描述函数的对外行为契约，而非复述内部实现。

## 适用场景

需要为一个已实现的目标函数补充或加固单元测试时；目标文件路径以 `<target-file>` 传入。

## 检查命令

```bash
npm test -- <target-file>
```

## 退出条件

- 新增测试全部通过。
- 覆盖正常、边界、错误三类用例。
- 检查命令退出码为 0。

## 执行步骤

Step 1: 运行检查命令，捕获输出，确认目标函数当前测试状态与缺失的覆盖。
Step 2: 分析函数的对外行为与契约，列出边界（空值、零、负数、极值、类型边界）和错误路径（非法输入、异常、并发），而非只测快乐路径。
Step 3: 生成最小且可读的测试用例，命名应表达被验证的行为；让检查命令通过。
Step 4: 重新运行检查命令；若仍有用例失败或覆盖缺口且未达最大迭代次数，回到 Step 2 补充或修正。
Step 5: 若达到最大迭代次数仍有测试未通过，停止并报告剩余失败用例与可疑的实现缺陷，不要删测试来凑绿。

## 常见陷阱

- 测试实现而非行为：断言内部私有状态或调用顺序，导致重构即脆裂。
- 只覆盖快乐路径：忽略边界与错误输入，留下隐性回归。
- 过度 mock：把被测对象桩化到只剩自我验证，失去真实意义。

## 注意事项

- 发现的真实实现缺陷应报告，而非用宽松断言绕过。
- 测试须独立可重复，不依赖执行顺序或外部状态。
- 不要为追求覆盖率写入无意义的琐碎断言。

- 收敛保护：若同一检查以相同根因连续两次迭代失败，应更换思路或停止上报，而非机械地原样重试。
- 预算纪律：遵守宿主 harness 的 token / 成本 / 时间预算；预算耗尽视为「停止并上报」信号，而非重试信号。
- 终态明确：循环只能以「成功 / 受阻 / 耗尽」三种终态结束；停滞或预算耗尽绝不能被报告为成功。
