# 收件箱清零循环

**分类:** 效率与生产力
**标识符:** `inbox-zero-loop`
**最大迭代次数:** 50

## 目标

将收件箱中每一封未读可执行邮件处理至零：每封都被回复、归档、委派或安排为待办，没有任何邮件处于"未决定"状态。成功意味着收件箱里不再有待办事项堆积。

## 适用场景

在专门处理邮件的时段使用，目标是把收件箱清零而非仅仅"减少未读数"。

## 检查命令

```bash
python scripts/inbox_check.py
```

## 退出条件

- 收件箱可执行邮件数为零，脚本退出码为 0。
- 每封邮件都已做出明确处置（回复/归档/委派/安排）。
- 不存在"已读但未决定"的遗留邮件。

## 执行步骤

Step 1: 运行 `python scripts/inbox_check.py`，捕获剩余可执行邮件数量与列表。
Step 2: 取一封未处理邮件，分析所需处置：需要回复、可归档（无需动作）、应委派给他人、还是需要安排为带截止日期的待办。
Step 3: 执行最小处置：发送回复、归档、转交委派、或新建带截止日期的待办，然后将其移出收件箱，绝不靠批量归档掩盖未决事项。
Step 4: 重新运行校验；若仍有可执行邮件且未达最大迭代次数，回到 Step 2。
Step 5: 若达到最大迭代次数仍未清零，停止并报告剩余阻塞项（如需他人输入才能回复的邮件），不要无限循环。

## 常见陷阱

- 不做决定就归档，只是把工作藏起来，并非真正清零。
- 对所有邮件一律回复，忽略了本应委派或安排的。
- 卡在逐字阅读长邮件线程上，迟迟不做处置决定。
- 把"已读"当成"已处理"，留下未决定的邮件。

## 注意事项

- "清零"指可执行项为零，不是未读数为零（纯通知/订阅可批量归档）。
- 委派或安排的待办必须有明确责任人与截止日期。
- 涉及敏感或机密内容的邮件，处置时遵守相应合规要求。

- 收敛保护：若同一检查以相同根因连续两次迭代失败，应更换思路或停止上报，而非机械地原样重试。
- 预算纪律：遵守宿主 harness 的 token / 成本 / 时间预算；预算耗尽视为「停止并上报」信号，而非重试信号。
- 终态明确：循环只能以「成功 / 受阻 / 耗尽」三种终态结束；停滞或预算耗尽绝不能被报告为成功。
