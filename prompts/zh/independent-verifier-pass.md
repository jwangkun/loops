# 独立验证通过

**分类:** 维护
**标识符:** `independent-verifier-pass`
**最大迭代次数:** 1

## 目标

以独立验证者身份执行一次完整的构建、lint 与测试，确认全部通过。判定只依据命令的真实退出码与输出，不接受"应该没问题"的推断或缓存结果。

## 适用场景

在合并、发布或交付前，对仓库做一次干净、可信的端到端验证时使用。本循环为单次验证，不进行修复迭代。

## 检查命令

```bash
npm run build && npm run lint && npm test
```

## 退出条件

- `npm run build`、`npm run lint`、`npm test` 三者依次全部退出码为 0。
- 不接受跳过任一环节或用缓存替代真实运行。
- 任一环节失败即视为整体未通过，需如实记录失败点。

## 执行步骤

Step 1: 以验证者身份按顺序运行 `npm run build && npm run lint && npm test`，逐条捕获每个命令的退出码与输出。
Step 2: 若全部退出码为 0，记录为通过并结束。
Step 3: 若任一命令失败，精确定位首个失败环节（构建/lint/测试）与报错信息，不在此循环内尝试修复。
Step 4: 如实汇报失败环节、退出码及关键错误片段，交由后续修复循环处理。
Step 5: 不进行第二次重试或自我安慰式重跑；一次未通过即如实上报。

## 常见陷阱

- 看到"上一次通过了"就跳过验证，忽略了环境或代码已变化。
- 把构建缓存或增量结果当作完整验证的等价物。
- lint/测试失败时自行判断"无关紧要"而忽略。
- 在本循环内顺手修复，模糊了"验证"与"修复"的职责边界。

## 注意事项

- 本循环只验证，不修复；保持验证者的独立性。
- 必须从干净状态运行，避免缓存掩盖真实问题。
- 任一环节失败立即停止后续环节的判定（因 `&&` 已短路），并明确报告。
- 汇报须包含命令、退出码与失败摘要，便于下游决策。
