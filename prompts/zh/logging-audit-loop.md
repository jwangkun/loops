# 日志审计循环

**分类:** 后端与API开发
**标识符:** `logging-audit-loop`
**最大迭代次数:** 8

## 目标

确保所有关键业务路径（鉴权、支付、状态变更、错误分支）都产出结构化、可被日志系统检索解析的日志，而非散落的字符串拼接或裸 `console.log`。成功意味着 `lint:logging` 全量通过，且新增/修改的日志包含必需字段（级别、事件名、可追踪 ID）。

## 适用场景

新增或改动关键路径逻辑后、排查线上事故需要可检索日志时、或团队约定结构化日志规范并需要强制落地时使用。

## 检查命令

```bash
npm run lint:logging
```

## 退出条件

- `lint:logging` 退出码为 0。
- 所有关键路径日志均使用批准的结构化 logger。
- 无裸 `console.log`、字符串拼接日志或缺失必需字段的日志语句。

## 执行步骤

Step 1: 运行 `npm run lint:logging`，捕获完整输出与失败文件/行号。
Step 2: 逐条分析失败并区分类型：裸 `console.*`、字符串拼接日志、缺失 `level`/`event`/`traceId` 字段，或日志中包含敏感数据。
Step 3: 用团队批准的结构化 logger 替换，补齐缺失字段，确保不含 PII/密钥；只做最小改动，不重写无关代码。
Step 4: 重新运行 `npm run lint:logging`；若仍有失败且未达最大迭代次数，回到 Step 2。
Step 5: 达到最大迭代次数仍未通过，停止并汇总剩余失败清单与原因，不要无限循环。

## 常见陷阱

- 在日志中打印密码、token、个人身份信息（PII）或完整请求体，违反合规与安全。
- 结构化日志缺失 `traceId`/`requestId`，导致跨服务链路无法串联。
- 把异常对象直接拼接进字符串，丢失堆栈与字段；应结构化记录 `error.message` 与 `stack`。
- 为通过 lint 而降级或删除日志，掩盖了真实问题。

## 注意事项

- 仅替换日志语句，不借机改动业务逻辑或日志阈值。
- 结构化字段名需与团队日志规范及采集端约定一致。
- 敏感数据需脱敏后记录，或在更高层做白名单过滤。
