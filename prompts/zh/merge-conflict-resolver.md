# 合并冲突解决

**分类:** Pull Request  
**标识符:** `merge-conflict-resolver`  
**最大迭代次数:** 10

## 目标

将当前分支变基(rebase)到最新的main之上，逐一解决所有冲突，并使全量测试通过。完成后分支历史线性、无残留冲突标记，且语义正确而非仅仅是文本拼接。

## 适用场景

当main有新提交、当前分支需要同步时使用。优先用rebase保持线性历史；冲突较多时可分批处理。

## 检查命令

```bash
npm test
```

## 退出条件

rebase成功完成(无未解决冲突、无残留冲突标记<<<<<<< / ======= / >>>>>>>)，且检查命令退出码为0。

## 执行步骤

Step 1: 执行git fetch后git rebase main；若产生冲突，用git status列出冲突文件清单。
Step 2: 一次处理一个文件：阅读双方的改动意图，优先判断应保留ours、incoming还是双方合并，避免无脑二选一。
Step 3: 解决时保证语义正确：同步被重命名的符号、调整调用点、补回被双方都需要的逻辑；删除所有冲突标记。
Step 4: 对已解决的文件git add，全部解决后运行检查命令；失败则定位首个失败用例并修复。
Step 5: 若仍有冲突或测试未通过且未达10次迭代，回到Step 2；若rebase无法推进(如需人工裁决的历史分叉)，执行git rebase --abort并停止，向用户报告阻塞点，不无限循环。

## 常见陷阱

- 无脑保留一方：盲目选ours或theirs，丢失另一方的关键改动。
- 只删冲突标记不解决语义：文本看起来干净，运行时仍错误。
- 一次git add全部：把未真正解决的文件混入提交，掩盖问题。
- 解决后不重测：以为无冲突标记即完成，忽略语义回归。

## 注意事项

- 优先理解双方意图再决策；遇到不确定的语义冲突，宁可中止(--abort)并询问，也不要猜测合并。
- 每解决一个文件即验证其可编译/可加载，再进入下一个。
- 不要在解决冲突的过程中夹带无关重构，保持改动可追溯。
- 若冲突源于大规模重命名/移动，先用git log --follow理清历史再决策。
