# 编辑后测试守卫

**分类:** 测试
**标识符:** `post-edit-test-guard`
**最大迭代次数:** 3

## 目标

每次代码编辑后，仅运行与被改动文件相关的测试，并确保这些测试全部通过、退出码为 0。这是防止局部修改引入回归的轻量级守卫，目标是最小成本地确认"我改的地方没坏"。

## 适用场景

在开发会话中频繁编辑代码时使用，作为提交前或合并前的最后一道快速防线；尤其适合在每次保存/编辑后自动触发。

## 检查命令

```bash
npm test -- --findRelatedTests <files>
```

## 退出条件

- 针对被改动文件的关联测试全部通过，退出码为 0。
- 未将任何失败用例改为 skip 或注释以"通过"。
- 命令实际执行了（非空运行），关联测试集合非空。

## 执行步骤

Step 1: 确定本次编辑改动的文件列表 `<files>`，运行检查命令，捕获输出与退出码。
Step 2: 分析失败：区分本次编辑引入的回归（改动逻辑/签名/导出导致）与既有失败（改动前就坏）。若怀疑是既有失败，可对改动前版本单独验证以确认。
Step 3: 对本次编辑引入的失败做最小修复——通常是补全改动遗漏的类型/导出、修正调用方或更新对应测试。绝不要用 `.skip`、放宽断言或 mock 掉真实失败点来掩盖。
Step 4: 重新运行检查命令；若仍有失败且未超过最大迭代次数，回到 Step 2。
Step 5: 达到最大迭代仍未通过时停止，列出剩余失败项，并明确区分"本次编辑引入的回归"与"改动前既有的失败"。不要无限循环。

## 常见陷阱

- `<files>` 列表不准确（漏改或漏传文件），导致关联测试没跑到，给出假绿。
- 把既有失败误判为本次回归，浪费迭代去修不属于本次改动的问题。
- 用 `.skip` 或放宽断言让测试"通过"，掩盖真实回归。
- 改动了公共 API 但只跑了直接关联文件，遗漏了间接依赖方的测试。

## 注意事项

- 这是局部守卫，不替代完整测试套件；提交前仍应跑全量测试。
- 仅修复与本次编辑直接相关的问题，不借机重构无关代码。
- 若关联测试集为空，应警惕——可能是依赖关系未识别，而非真的无测试。

- 收敛保护：若同一检查以相同根因连续两次迭代失败，应更换思路或停止上报，而非机械地原样重试。
- 预算纪律：遵守宿主 harness 的 token / 成本 / 时间预算；预算耗尽视为「停止并上报」信号，而非重试信号。
- 终态明确：循环只能以「成功 / 受阻 / 耗尽」三种终态结束；停滞或预算耗尽绝不能被报告为成功。
