# PR自我审查

**分类:** 持续集成/持续部署  
**标识符:** `pr-self-review`  
**最大迭代次数:** 6

## 目标

在当前分支与main的差异(diff)上完成三轮独立、严格的自我审查，每轮聚焦不同维度(正确性、可维护性、风险)，并在退出前修复所有发现的问题。审查对象仅为本次改动，不重写无关代码。

## 适用场景

当你即将请求他人审查或合并PR之前，先用此循环自检，避免把明显问题丢给审查者。也可在CI/审查者反馈后再次运行。

## 检查命令

```bash
git diff main...HEAD
```

## 退出条件

连续三轮审查分别覆盖正确性、可维护性、风险点，且每轮均无新增需修复项；所有已发现的问题均已修复并通过本地验证。

## 执行步骤

Step 1: 运行检查命令捕获完整diff，逐个文件理解改动意图，不读未改动的文件。
Step 2: 第一轮审查正确性：边界条件、空值/null、错误处理、并发与竞态、与测试是否匹配。
Step 3: 第二轮审查可维护性：命名、重复代码、函数长度、注释缺失、魔法数字、命名一致性。
Step 4: 第三轮审查风险点：安全(注入、鉴权)、性能、兼容性破坏、日志与敏感信息泄漏、回滚难度。
Step 5: 对每个发现做最小修复，修复后重新运行检查命令确认diff收敛；若仍有问题且未达6次迭代，回到Step 2。
Step 6: 若达到6次迭代仍有未解决问题，停止并列出剩余阻塞项，不无限循环。

## 常见陷阱

- 只读diff不看上下文：脱离调用点判断改动的副作用。
- 橡皮图章：把"看起来没问题"当成审查通过，未真正追问每处改动的原因。
- 顺手重构无关代码：扩大diff范围，掩盖真实改动并增加审查与回滚成本。
- 忽略测试与改动是否一致：改了实现却忘了更新或新增测试。

## 注意事项

- 审查的是diff本身，不要重写整个文件。
- 修复必须是真实修复，禁止注释掉失败测试或删除断言来"通过"。
- 涉及破坏性变更或安全修复时，在描述中显式标注，不要藏在改动里。
