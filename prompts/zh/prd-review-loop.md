# PRD审查循环

**分类:** 产品与设计
**标识符:** `prd-review-loop`
**最大迭代次数:** 6

## 目标

让 PRD 在完整性、清晰度与可开发性三方面全部通过 `prd_check.py`，达到开发可直接开工的状态。每轮只针对报告的缺陷做最小补充——补齐缺失章节、为需求补验收标准、消除歧义——而非整篇重写。成功即所有审查项通过。

## 适用场景

在 PRD 定稿前、需求评审或交接开发时使用，尤其当涉及新功能、跨团队依赖或验收门槛要求时。

## 检查命令

```bash
python scripts/prd_check.py
```

## 退出条件

- `prd_check.py` 退出码 0，所有审查项通过。
- 每条需求均配有可验证的验收标准。
- 关键章节（背景、范围、非目标、依赖）齐备无空白。

## 执行步骤

Step 1: 运行检查，完整捕获输出（缺失章节、无验收标准的需求、歧义表述、未界定范围等）。
Step 2: 逐条分析失败：区分章节缺失、需求无验收标准、边界/非目标未定义、依赖与风险未标注；定位到具体位置与原因。
Step 3: 用最小改动修复该处——补章节、为需求补可验证验收标准、明确非目标——而非推翻重写。
Step 4: 重新运行检查；若仍失败且未达最大迭代次数，回到 Step 2。
Step 5: 达到最大迭代仍未通过则停止，报告剩余阻塞项（章节、需求、缺失项），不要无限循环。

## 常见陷阱

- 写了需求却没写验收标准，开发与测试无法判断"做完了"。
- 范围与非目标未界定，导致镀金或范围蔓延。
- 把实现方案写成需求，过早绑定技术选型。
- 依赖、约束与风险未显式列出，下游团队踩坑。

## 注意事项

- 需求基于需求方提供的事实与目标；缺失信息先确认，不要自行假设。
- 验收标准须可验证，避免"体验良好"等主观表述。
- 改动保持可追溯，重大范围变更需回流评审。
