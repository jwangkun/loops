# Pre-commit守卫

**分类:** 持续集成/持续部署  
**标识符:** `pre-commit-guard`  
**最大迭代次数:** 3

## 目标

在每次git提交之前运行测试套件，只有当测试退出码为0时才允许提交。任何失败都必须先修复，杜绝把红色状态推进版本库。

## 适用场景

作为提交前的最后一道门禁，在你即将执行git commit时运行。适合本地提交前自检，避免推上去后才被CI发现。

## 检查命令

```bash
npm test
```

## 退出条件

检查命令退出码为0，方可执行git commit；否则提交被阻止。

## 执行步骤

Step 1: 在git commit之前运行检查命令，捕获完整输出与退出码。
Step 2: 若退出码非0，定位第一个失败用例，阅读其错误栈与断言信息，判断是代码缺陷还是测试本身的问题。
Step 3: 对代码缺陷做最小修复；若是测试本身失效，修正测试使其反映真实预期，禁止删除断言或skip来掩盖。
Step 4: 重新运行检查命令；若仍失败且未达3次迭代，回到Step 2。
Step 5: 若3次迭代后仍失败，停止提交，向用户报告阻塞原因与建议，不强行提交。

## 常见陷阱

- 用--no-verify绕过门禁：把红色状态提交进库，把问题留给CI或队友。
- 删除断言或skip失败用例：让测试变绿却失去保护价值。
- 把测试本身写错当成代码缺陷：未区分实现bug与测试期望漂移，修错对象。
- 只跑单文件测试：以为局部通过即可，忽略跨模块回归。

## 注意事项

- 提交门禁不可绕过；若确需临时跳过(如紧急hotfix流程)，必须显式说明并尽快补回。
- 修复优先于提交，禁止先提交再修。
- 若测试套件执行过慢，应优化套件而非放宽门禁。

- 收敛保护：若同一检查以相同根因连续两次迭代失败，应更换思路或停止上报，而非机械地原样重试。
- 预算纪律：遵守宿主 harness 的 token / 成本 / 时间预算；预算耗尽视为「停止并上报」信号，而非重试信号。
- 终态明确：循环只能以「成功 / 受阻 / 耗尽」三种终态结束；停滞或预算耗尽绝不能被报告为成功。
