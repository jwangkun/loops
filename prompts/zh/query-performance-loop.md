# 查询性能循环

**分类:** 数据库与数据
**标识符:** `query-performance-loop`
**最大迭代次数:** 8

## 目标

将 `benchmark:queries` 中超阈值的所有查询优化到阈值以下，且不引入新的性能或正确性回归。成功意味着基准测试全量通过，最慢查询的执行时间、扫描行数与 I/O 均在可接受范围内。

## 适用场景

新增查询或改动 schema 后、基准测试出现退化时、或需要在上线前守住查询延迟预算时使用。

## 检查命令

```bash
npm run benchmark:queries
```

## 退出条件

- `benchmark:queries` 所有查询均低于设定阈值（exit 0）。
- 无查询触发全表扫描或 N+1 模式。
- 优化基于执行计划验证，而非盲目猜测。

## 执行步骤

Step 1: 运行 `npm run benchmark:queries`，捕获超阈值查询、耗时、调用频次与所在代码位置。
Step 2: 对每个慢查询获取并阅读执行计划（`EXPLAIN`）：确认是否缺索引、是否存在隐式类型转换、是否发生 N+1、是否选错索引。
Step 3: 做最小且正确的修复：补充针对性索引、重写查询（避免 `SELECT *`、限制返回行数、消除子查询），或修正 ORM 的预加载策略；索引命名与迁移需符合规范。
Step 4: 重新运行 `npm run benchmark:queries`；若仍有超阈值且未达最大迭代次数，回到 Step 2。
Step 5: 达到最大迭代次数仍未达标，停止并报告剩余慢查询、执行计划证据与建议，不要无限循环。

## 常见陷阱

- 不看执行计划就盲目加索引，导致索引冗余、写入变慢且仍无效果。
- 添加索引却遗漏相应迁移脚本，导致生产环境与本地不一致。
- 优化查询时改变结果集语义（如误改 `JOIN` 类型或过滤条件），引入正确性回归。
- 只盯单次执行时间，忽略高频调用带来的累积负载。

## 注意事项

- 所有索引变更必须通过迁移脚本落地并评审，不手动改库。
- 优化前确认基准数据量具有代表性，避免在小数据集上得出错误结论。
- 不为通过基准而关闭安全机制（如参数化、权限过滤）。
