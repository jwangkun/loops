# 限流实施循环

**分类:** 后端与API开发
**标识符:** `rate-limit-enforcer`
**最大迭代次数:** 8

## 目标

确保每个对外暴露的公共端点都挂载了限流策略，按端点分级配置上限，能在压测下正确返回 429，且未保护端点数为零。

## 适用场景

当新增了公开端点却未配置限流，或安全/压测发现某些路由可被无限制调用时使用。也适用于上线前的防护加固。

## 检查命令

```bash
npm run test:rate-limit
```

## 退出条件

- `npm run test:rate-limit` 退出码为 0。
- 所有公共端点均挂载限流中间件。
- 超过阈值的请求稳定返回 429，且带 Retry-After 头。

## 执行步骤

Step 1: 运行 `npm run test:rate-limit`，记录未受保护端点、阈值设置不当以及未返回 429 的用例。
Step 2: 对照路由清单，逐个确认是否挂载限流、限流维度（IP/用户/端点）与阈值是否合理。
Step 3: 用最小改动为缺失端点挂载限流中间件，按风险分级设置阈值，并确保响应符合规范（429 + Retry-After）；不要只给部分路由加限流。
Step 4: 重新运行检查命令；若仍失败且未达最大迭代次数，回到 Step 2。
Step 5: 达到最大迭代次数仍未通过时停止，汇报剩余未保护端点与失败用例，不要无限循环。

## 常见陷阱

- 只给少数高风险端点加限流，遗漏其余公共路由。
- 限流维度选错（如仅按 IP，被 NAT/代理绕过）。
- 阈值设置过高使限流形同虚设，或过低误伤正常用户。
- 返回 429 时未带 Retry-After，客户端无法退避。

## 注意事项

- 限流应作用于所有公共入口，包括内部暴露到外部的端点。
- 区分认证用户与匿名用户的限流策略。
- 不要为通过测试而临时调高阈值或禁用限流。
- 多实例部署下限流计数需共享存储（如 Redis）。

- 收敛保护：若同一检查以相同根因连续两次迭代失败，应更换思路或停止上报，而非机械地原样重试。
- 预算纪律：遵守宿主 harness 的 token / 成本 / 时间预算；预算耗尽视为「停止并上报」信号，而非重试信号。
- 终态明确：循环只能以「成功 / 受阻 / 耗尽」三种终态结束；停滞或预算耗尽绝不能被报告为成功。
