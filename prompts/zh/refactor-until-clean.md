# 重构直到干净

**分类:** 代码质量
**标识符:** `refactor-until-clean`
**最大迭代次数:** 10

## 目标

在不改变外部行为的前提下，持续消除目标模块中的代码坏味道，直到 lint 与测试全部通过、且关键指标（复杂度、重复、函数长度）有可度量的改善。正确性由测试套件守护。

## 适用场景

当某模块可读性差、重复多、函数过长或难以扩展，但行为正确、有测试覆盖时使用。缺乏测试的模块应先补测试再进入本循环。

## 检查命令

```bash
npm run lint && npm test
```

## 退出条件

- `npm run lint` 与 `npm test` 均退出码为 0。
- 至少一项指标（圈复杂度 / 重复率 / 最长函数）较起点下降。
- 没有引入任何新的 lint 告警或失败测试。
- 达到 10 次仍未达标时停止并汇报。

## 执行步骤

Step 1: 运行 `npm run lint && npm test`，确认起点为绿，记录基线指标。
Step 2: 识别当前最严重的一个坏味道（长函数、重复块、过深嵌套、命名歧义等），定位其最小范围。
Step 3: 对该范围应用最小、保持行为的重构（提取函数、内联、改名、移动等）；先跑测试再提交本轮。
Step 4: 重新运行检查命令并对比指标；若 lint/测试仍绿且未达标，回到 Step 2。
Step 5: 达到 10 次仍未达标，或测试转红且无法在当轮修复时，停止并汇报剩余坏味道与阻塞。

## 常见陷阱

- 重构引入行为变化却未被发现——始终以测试套件为护栏，转红立即回滚当轮改动。
- 一次性大重构，丢失中间可验证步骤，回滚与审查都困难。
- 只追求"看起来更短"，指标无实际改善，空耗迭代。
- 改动蔓延到模块外，触发跨模块回归。

## 注意事项

- 严格保持外部行为不变：公共 API 签名、返回值、副作用、错误类型均不得变。
- 每轮只动一个坏味道，保持改动可独立回滚。
- 任何重构前先确认测试覆盖该路径；无覆盖先补测试。
- 不为通过 lint 而压制规则，优先真正修正。

- 收敛保护：若同一检查以相同根因连续两次迭代失败，应更换思路或停止上报，而非机械地原样重试。
- 预算纪律：遵守宿主 harness 的 token / 成本 / 时间预算；预算耗尽视为「停止并上报」信号，而非重试信号。
- 终态明确：循环只能以「成功 / 受阻 / 耗尽」三种终态结束；停滞或预算耗尽绝不能被报告为成功。
