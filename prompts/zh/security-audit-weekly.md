# 每周安全审计

**分类:** 安全
**标识符:** `security-audit-weekly`
**最大迭代次数:** 1

## 目标

基于 `npm audit --json` 的结构化输出，产出一份每周依赖漏洞审计摘要：按严重性分类、列出受影响包与可利用性、给出可执行的修复优先级与计划。摘要面向工程与安全负责人决策。

## 适用场景

作为每周例行安全巡检运行；不用于自动修复（修复请使用 npm-audit-fix-loop），也不替代 CI 门禁。

## 检查命令

```bash
npm audit --json
```

## 退出条件

- 已生成结构化审计摘要，涵盖全部 high 与 critical advisory。
- 每条 advisory 标注严重性、受影响路径、是否可达、建议修复版本与建议行动。
- 已按优先级给出本周修复计划（立即修复 / 下个迭代 / 接受风险并说明理由）。

## 执行步骤

Step 1: 运行检查命令，捕获 JSON 输出；解析 `metadata.vulnerabilities` 与 `advisories`/`vulnerabilities` 节点。
Step 2: 按严重性分组，对每条 high/critical advisory 评估受影响依赖路径、是否进入生产运行时、是否存在可用修复版本；低危/提示级做汇总即可。
Step 3: 针对每条高优先级项撰写建议行动（升级版本 / 替换包 / 暂时接受并记录风险理由），不得编造不存在的修复版本。
Step 4: 重新运行检查命令以确认输出与摘要一致（仅 1 次迭代，故为验证而非循环）。
Step 5: 若达到最大迭代次数（1 次）仍未生成完整摘要，停止并报告缺失的部分，不得无限循环。

## 常见陷阱

- 直接转述 `npm audit` 的人类可读输出而不解析 JSON，会遗漏嵌套依赖与可达性信息。
- 将"有 advisory"等同于"可被利用"：需判断漏洞代码路径是否真正进入生产运行时。
- 为没有修复版本的 advisory 编造"升级到 x.y.z"建议，会误导后续修复工作。
- 忽略 devDependency 中的高危项有时是合理的，但必须在摘要中明确说明理由而非直接省略。

## 注意事项

- 摘要应可被非安全背景的工程师理解；关键结论放在开头。
- 涉及真实可利用漏洞时，在摘要中标注是否需要人工安全负责人介入。
- 不要在摘要中输出明文密钥或敏感环境信息。

- 收敛保护：若同一检查以相同根因连续两次迭代失败，应更换思路或停止上报，而非机械地原样重试。
- 预算纪律：遵守宿主 harness 的 token / 成本 / 时间预算；预算耗尽视为「停止并上报」信号，而非重试信号。
- 终态明确：循环只能以「成功 / 受阻 / 耗尽」三种终态结束；停滞或预算耗尽绝不能被报告为成功。
