# Ship PR直到通过

**分类:** 持续集成/持续部署
**标识符:** `ship-pr-until-green`
**最大迭代次数:** 15

## 目标

从实现变更到 PR 所有 CI 检查变绿的端到端交付：完成实现、本地验证、推送、开 PR，并循环修复 CI 失败，直到 `gh pr checks` 显示全部通过且 PR 处于可合并的健康状态。

## 适用场景

当一个任务需要从"写代码"一路推进到"PR CI 全绿、可评审合并"时使用，适合一次完整的小颗粒交付。

## 检查命令

```bash
gh pr checks <PR-NUMBER>
```

## 退出条件

- PR 所有检查均为 `pass`；无 `fail` 之外的失败项。
- PR 处于 `OPEN` 状态且无阻塞型 CI 失败。

## 执行步骤

Step 1: 实现变更并运行本地测试/lint/类型检查；确认本地通过后再推送分支。
Step 2: 若尚未开 PR 则用 `gh pr create` 创建；运行 `gh pr checks <PR-NUMBER>` 捕获各检查名称与状态（若仍在进行中，等待后重查）。
Step 3: 对每个失败的检查，读取其日志与关联 job，判断是本 PR 代码缺陷还是基础设施/上游问题；只对本 PR 引入的真实缺陷做最小修复（绝不靠跳过、放宽校验或 `|| true` 制造绿色）。
Step 4: 本地复跑相关测试通过后提交并推送；回到 Step 2 重新检查，直到全部通过或达到最大迭代次数。
Step 5: 若达到最大迭代次数仍有检查失败，停止并报告：PR 链接、剩余失败检查、日志关键报错、已尝试的修复及未解决阻碍，不要无限循环。

## 常见陷阱

- 本地只跑了单元测试就推送，忽略了 CI 中的 lint、typecheck、集成测试或跨平台矩阵。
- 把 flaky 检查或配额/网络导致的失败当成代码问题去改实现。
- 一次提交里塞入多个无关改动，导致失败难以归因、评审困难。
- 失败源自与目标分支冲突或上游 main 已坏，却在本 PR 内反复修改。

## 注意事项

- PR 必须基于最新目标分支；若发现冲突或 base 已坏，先 rebase 或同步再继续。
- 禁止用跳过检查、强制退出码 0、注释掉测试等方式伪造通过。
- 每次推送聚焦于一个根因修复，保持提交历史清晰、便于评审。
- 合并策略遵循仓库约定（squash/rebase/merge），不要自行改写他人已评审的提交。
