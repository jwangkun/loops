# Spec优先发布

**分类:** 持续集成/持续部署  
**标识符:** `spec-first-ship`  
**最大迭代次数:** 20

## 目标

将spec.md中列出的每一条需求都实现、验证并在文档中勾选，使需求清单与代码状态保持完全一致。完成时没有任何未勾选的需求项，且测试全绿。

## 适用场景

当存在一份作为唯一真实来源的需求文档(spec.md)时使用。每次循环围绕"下一个未勾选项"推进，避免功能漂移或漏交付。

## 检查命令

```bash
npm test
```

## 退出条件

spec.md中所有需求项均已勾选[ x ]，且检查命令退出码为0。

## 执行步骤

Step 1: 读取spec.md，找出第一个未勾选的需求项(标记为[ ])；明确其验收标准。
Step 2: 以最小改动实现该项需求，仅触及与其相关的文件，不提前实现后续项。
Step 3: 运行检查命令；失败则定位首个失败用例并修复，禁止跳过或xdescribe屏蔽。
Step 4: 实现通过后，将spec.md中该项从[ ]改为[ x ]，记录验证方式(命令/用例)。
Step 5: 若仍有未勾选项且未达20次迭代，回到Step 1；若达20次仍有未完成项，停止并列出剩余项，不无限循环。

## 常见陷阱

- 偷偷勾选未实现项：用打勾掩盖空实现，导致需求清单不可信。
- 一次塞入多项：一个迭代改动过多，定位回归困难。
- 跳过失败测试：用skip/xdescribe绕过，破坏"测试=验收"的契约。
- 需求模糊时凭猜测实现：未明确验收标准就动手，实现方向偏离。

## 注意事项

- spec.md是唯一真实来源；代码与文档冲突时以验收标准为准，而非随意改文档。
- 单次迭代只处理一个需求项，保持diff小且可审查。
- 勾选前必须运行检查命令并真实通过，不接受"应该没问题"。

- 收敛保护：若同一检查以相同根因连续两次迭代失败，应更换思路或停止上报，而非机械地原样重试。
- 预算纪律：遵守宿主 harness 的 token / 成本 / 时间预算；预算耗尽视为「停止并上报」信号，而非重试信号。
- 终态明确：循环只能以「成功 / 受阻 / 耗尽」三种终态结束；停滞或预算耗尽绝不能被报告为成功。
